# 实时协作白板 · 面试自述稿

> 5 分钟讲清这个项目：做了什么、难点在哪、怎么证明它work。

---

## 一句话介绍

一个支持 50 人同房间实时绘制、光标同步、断网离线编辑自动合并、操作历史回放的
协作白板。技术栈 Vue3 + Canvas + Yjs(CRDT) + Node 信令 + Redis Pub/Sub。

---

## 30 秒技术亮点

| 维度 | 实现 |
|---|---|
| 冲突处理 | CRDT 天然无冲突，靠**数据结构选型**把冲突域切到最小 |
| 离线支持 | 断网本地照常写，重连按 state vector 求差集双向同步，**不覆盖任何一方** |
| 渲染性能 | 双层 Canvas（已提交 / 预览解耦）+ 视口裁剪 + 采样抽稀 |
| 传输效率 | 同 tick 消息合并，扇出次数降低数十倍 |
| 横向扩展 | Redis Pub/Sub 广播总线，任意实例可接入同一房间，**无 Redis 自动降级** |

## 深挖点 1：你说你用了 Yjs，你自己做了什么？

**这是面试官最可能追问的问题。** 明确划清边界：

> Yjs 只提供 CRDT 数据结构和增量编解码。信令协议、广播总线、连接生命周期管理、
> 渲染架构、回放引擎、延迟度量体系全部是我写的。

具体清单（对应 `docs/ARCHITECTURE.md` 第 11 节踩坑记录）：

1. **信令协议层**（`server/src/room.js`）
   解析 sync / awareness 消息，处理 sync step1&2 握手，用事务 `origin` 区分更新来源防止回环广播。
2. **广播总线抽象**（`server/src/bus.js`）
   Redis Pub/Sub 与内存 EventEmitter 同接口，未配置 Redis 自动降级为零依赖单进程模式，
   降级路径**显式打日志**（静默降级会让生产环境的横向扩展悄悄退化成单机）。
3. **连接生命周期管理**
   指数退避重连、消息体积上限、心跳清理半开连接（否则"幽灵用户"会一直占位显示在线）。
4. **双层 Canvas 渲染器**（`web/src/components/Renderer.js`）
   base 层画已提交内容、draft 层画当前笔迹，网络更新不打断本地绘制的 60fps 手感。
5. **回放引擎**（`web/src/components/Replay.js`）
   独立文档渐进重放。关键在于**CRDT 文档无法"撤销"已合并的更新**，
   所以时间轴向前跳是 O(1)、向后跳必须重建文档——这个非对称性是设计时就要想清楚的。
6. **延迟度量体系**
   基于探针笔迹的端到端"操作可见延迟"，并识别出三个度量陷阱（见下）。

## 深挖点 2：两个人同时在同一位置画，怎么处理冲突？

**关键认知：不是"处理"冲突，而是"避免"冲突。**

```js
// 不同人的笔迹是 Y.Array 中的不同元素 → 合并是并集，永不冲突
doc.getArray('strokes').push([stroke])

// 反例：整张画布存成一个 map
doc.getMap('canvas').set('strokes', [...])   // 两人并发改同一 key → LWW，一方成果全丢
```

**要点：数据结构选型直接决定冲突概率。**
冲突域要切得细到"两人不可能同时改同一处"。

对比方案：
- 锁 / 中心节点仲裁：牺牲可用性，且无法离线
- OT 转换：中心化 Transform 权威，转换表随操作类型组合爆炸
- CRDT：用元数据膨胀换"永不冲突"

## 深挖点 3：断网了用户还在画，联网后怎么合？

机制：离线时 WebSocket 断开，但**本地 Y.Doc 照常接收编辑**，
每次修改编码成携带因果信息的增量更新。重连时：

```
sync step1（交换 state vector）→ 双方计算差集 → step2 补齐
```

**不存在"谁覆盖谁"**——差集是集合运算，双方内容都保留。

**产品层面的坑（比技术更值钱）**：
UI 必须明确告知用户"你的编辑保存在本地"。否则用户以为白板卡死而刷新页面，
导致离线内容丢失。这是协作产品最容易犯的产品级错误。

## 深挖点 4：你的延迟数据是怎么测的？

**这里要主动讲"我避开了哪些陷阱"**，比只报数字更能体现工程素养：

**陷阱一：拿 ping 延迟冒充同步延迟。**
ping 只反映网络 RTT，不含服务端处理与渲染调度。→ 用探针笔迹测端到端可见时间。

**陷阱二：对每条操作都计时 → O(n²)。**
每次 update 全量遍历 strokes 找新元素，n 上千时压测客户端自己成为瓶颈，
测出的延迟反映的是客户端而非服务端。→ 改用固定间隔的探针笔迹。

**陷阱三：离线客户端污染样本。**
离线客户端重连后一次性收到大量历史更新，计入统计会产生数秒的虚假长尾。
→ 只统计在线期间的样本。

**陷阱四：固定 sleep 判定收敛 → 误报"未收敛"。**
100 人场景实测收敛只需 2.3s，但我最初用固定 4s 等待，
在 20 个客户端同时重连时误判为"未收敛"，差点去优化一个没问题的系统。
→ 改为轮询直到全员一致或超时。
**压测工具不准，会把正常的系统误报成有 bug。**

然后给出实测数据（必须说清环境）：

| 场景 | 连接 | CRDT 收敛 | 延迟 P50/P95/P99 | 离线合并 | 异步异常 |
|---|---|---|---|---|---|
| 50 人 + 10 人断网 | 50/50 | 全部一致 | 0.2 / 0.4 / 0.7 ms | 80/80 | 0 |
| 100 人 + 20 人断网 | 100/100 | 全部一致 | 0.1 / 0.2 / 0.3 ms | 160/160 | 0 |

> 本机 loopback 环境，反映的是**服务端处理能力上限**。
> 端到端延迟还要叠加网络 RTT，跨城 20–50ms。

### 加分项：你的 RTT 指标本身也踩过坑

如果面试官继续追问"那你怎么知道网络本身没问题"，可以讲这个：

我最初用 **awareness 通道**做 RTT 探针——客户端发一个带时间戳的 ping，
靠服务端中继回来算往返时间。结果页面上稳定显示 **200ms 左右的延迟**，
但压测里端到端同步延迟明明是亚毫秒级，两者对不上。

查下去发现：**服务端广播 awareness 时会排除消息来源连接**（防回环），
所以发起者永远收不到自己的回声。我读到的其实是"距上次 ping 多久"，
不是"往返了多久"——在 800ms 探测间隔下就显示成 200~800ms。

改法是自己加了一对扩展消息类型：

```
200 PING  客户端 → 服务端：varuint 时间戳
201 PONG  服务端 → 客户端：原样回显时间戳
```

服务端只解码后原样回显；客户端在 `provider.messageHandlers[201]`
注册处理器（y-websocket 官方只注册了 0~3，不注册会被丢弃并打印
`Unable to compute message`）。改完之后 RTT 稳定在 **0.4–1.3ms**，
和端到端同步延迟对上了。

> **这个案例的价值在于：功能完全正常、指标看起来"只是偏高"，
> 但那个数字是假的。** 大多数人不会去验证指标本身是否可信。
> 而这恰恰是"你真的做了这个项目"和"你跑了个 demo"的分界线。

## 深挖点 5：踩过什么坑？

讲一个最有技术含量的：**消息二次包裹**。

协议是 `[varuint type][varUint8Array payload]`，
但 `syncProtocol.writeUpdate()` 产出的**已经是完整 sync 消息**（内含子类型），
再套一层 `writeVarUint8Array` 就多出一个长度头 → 客户端解析字节错位 → `Unexpected end of array`。

症状极有迷惑性：**单客户端正常，多客户端一同步就崩**。

定位方式：把服务端发出的原始字节 hex dump 出来对照。
这一步值得强调——**没有原始字节 dump，我可能会一直怀疑是并发问题或内存问题。**

其他坑（挑 1-2 个）：
- Awareness 实例归属：给每个连接新建实例，其 update 事件不会触发房间广播，光标永远同步不了
- 共享 Awareness 被单连接 destroy：会摧毁整个房间的 awareness
- `y-websocket` 的 URL 约定会把房间名拼成路径段，serverUrl 里带 query 会错位
- **手动删 `awareness.meta` 造成幽灵成员**：清理断开连接的成员时，我手写了
  `states.delete()` + `meta.delete()`，但 `encodeAwarenessUpdate` 内部还要读
  `meta.get(clientID).clock` 来编码"该成员已离开"，于是抛 TypeError，
  **把整个清理流程中断**——连接断了，成员却永远显示在房间里。
  正解是用官方 `removeAwarenessStates()`：它保留 meta 的 clock，
  并自动触发 update 事件把"成员离开"广播出去。
  教训是：库的 API 内部维护着你不了解的不变量，绕过它手改内部状态就等于放弃了这层保证。
- **Vue 模板里的"伪响应式"导致整页白屏**：我最初把 `online`/`peers`/`stats`
  写成普通对象 `{ value: ... }`（手写响应式系统的习惯），
  Vue 3 只对 `ref`/`reactive` 解包。`peers` 被传给子组件后，
  子组件里 `props.peers.filter()` 直接 TypeError，组件渲染抛错，
  **整页白屏**。更迷惑的是服务端日志里一条浏览器连接都没有——
  因为异常发生在 WebSocket 建立之前。
  定位靠无头浏览器抓真实控制台错误，而不是读代码猜。

## 深挖点 6：还能怎么优化？

主动说出限制，比被问住好：
- 内存态存储 → 快照持久化
- 无鉴权 → JWT + 房间级 ACL
- 离线重连时全量广播 → 让客户端通过 sync step1/2 增量拉取
- 慢客户端无背压 → 按连接限流

## 可能被问到的技术追问

**Q：Yjs 的 update 为什么可以随便合并？**
A：因为 CRDT 的更新本身满足交换律、结合律、幂等性。
合并只是把多组"状态变更"打包传输，客户端应用结果与逐条应用相同。

**Q：为什么不自己实现 CRDT？**
A：至少数千行，且极易在"删除"和"嵌套结构"上出错。工程上正确分工是
不重复造轮子，但必须理解轮子的边界——比如 CRDT 无法撤销已合并的更新、
delete 是"标记删除"而非真删。

**Q：Redis Pub/Sub 和 Redis Streams 怎么选？**
A：Pub/Sub 是 fire-and-forget，不保证送达，重连丢消息。
本项目因为客户端有 sync step1/2 的兜底全量对齐，能容忍丢消息。
若要保证不丢，需要 Streams 或 Redis List。

**Q：多实例部署时，房间状态怎么共享？**
A：文档状态在每个实例的内存里，靠 Redis Pub/Sub 广播增量同步。
极端情况下两个实例同时收到同一房间的连接，会出现状态分叉——
生产环境需要做房间到实例的**一致性哈希路由**（sticky session），
这是我的方案里还没做的一环。
